## Executive Summary

This document outlines all data requirements from the UI/UX implementation, organized by data entity. The goal is to establish a **data schema that is normalized, consistent, and supports the business logic** defined in the business requirements.

## Data Entities Overview

### 1. Workspaces
**Business Logic:** Multi-tenant financial management. Each user belongs to multiple workspaces. Workspace is the primary data scoping unit.

**UI Components Using This Entity:**
- DashboardHeader (workspace selector pill)
- Workspace page (workspace list, create, invite members)

**Required Data:**
```typescript
interface Workspace {
  id: string;              // Primary key
  name: string;            // Display name
  icon: string;            // Emoji for UI (💰, 🏠, etc.)
  role: "owner" | "member"; // Only relevant for owner
}
```

**Questions for Backend:**
1. How should workspace switching be handled? Is it session-based or a separate table?
2. Should `workspace_members` be modeled as a junction table?
3. Are workspaces soft-deletable or cascade-delete only?
4. Should workspace settings (name, icon changes) be audited?

### 2. Wallets
**Business Logic:** A wallet represents a financial account (bank, e-wallet, cash, savings). Wallets belong to a workspace. All transaction amounts must sum to the wallet's computed balance.

**UI Components Using This Entity:**
- Dashboard wallet scroll cards (wallet type icons)
- WalletListItem (full-width row with icon, name, type, balance, transaction count)
- Wallet Detail page (balance hero, actions, monthly summary, transaction list)
- Add Transaction sheet (wallet dropdown for income/expense, transfer from/to for transfers)

**Required Data:**
```typescript
interface Wallet {
  id: string;              // Primary key
  name: string;            // Display name
  type: string;            // enum: "tunai", "rekening_bank", "e_wallet", "tabungan", "bisnis", "custom"
  balance: number;          // COMPUTED field (not stored)
  // Note: initial balance adjustments are NOT direct field edits - they are recorded as corrective transactions to preserve ledger integrity
  monthlyIncome: number;   // Optional: computed sum of income transactions for current month
  monthlyExpense: number;  // Optional: computed sum of expense transactions for current month
  createdAt: Date;         // Auto-set on creation
  updatedAt: Date;         // Auto-updated on edit (name, type only)
}
```

**Questions for Backend:**
1. How is `balance` computed? Should we store it as a cached value or calculate on the fly from transaction ledger?
2. If we cache `balance`, how do we invalidate it when transactions change?
3. Should wallet deletion be soft-delete (preserves history) or hard-delete (cascade)?
4. Should we track wallet type counts per user for the "4 wallets" display on dashboard?

### 3. Transactions
**Business Logic:** The atomic unit of the entire system. All balances, budgets, and goals derive from the transaction ledger. Transactions must be immutable for audit trail.

**UI Components Using This Entity:**
- Add Transaction sheet (type toggle, amount input, wallet/category pickers, date, notes)
- TransactionRow (transaction list item with category icon, name, amount with +/- and color)
- Wallet Transaction List (filtered by wallet)
- Dashboard Recent Transactions

**Required Data:**
```typescript
interface Transaction {
  id: string;              // Primary key
  name: string;            // Display name
  category: string;          // enum based on type
  type: string;            // enum: "income", "expense", "transfer_debit", "transfer_credit"
  amount: number;            // Always positive (sign handled at display)
  date: Date;               // Transaction date (not datetime for simplicity)
  notes: string | null;     // Optional free-text notes
  walletId?: string;         // For income/expense
  fromWalletId?: string;    // For transfer_debit
  toWalletId?: string;        // For transfer_credit
  transferId?: string;       // Links transfer_debit and transfer_credit (same UUID for both records)
  workspaceId: string;       // Foreign key to workspace (scoping)
  createdAt: Date;         // Auto-set
  updatedAt: Date;         // Auto-updated on edit
}
```

**Questions for Backend:**
1. How should we handle currency formatting (IDR)? Should it be stored in DB or formatted on display?
2. For transfers, should we ensure atomic insert of both debit and credit records in a DB transaction?
3. Should transactions support soft-delete (archived flag) or are they immutable?
4. How do we handle pagination for transaction lists (currently mocked at 20/page)?

### 5. Budgets
**Business Logic:** Budgets track spending limits per category, per month, per workspace. Budget progress is computed in real-time from expense transactions.

**UI Components Using This Entity:**
- Budget page (not yet implemented)
- Budget cards with progress bars (green < 80%, amber 80-100%, red > 100%)

**Required Data:**
```typescript
interface Budget {
  id: string;              // Primary key
  category: string;          // Expense category from enum
  limitAmount: number;      // Target spending limit (positive)
  month: string;            // YYYY-MM format
  workspaceId: string;       // Foreign key
  createdAt: Date;         // Auto-set
  updatedAt: Date;         // Auto-updated on edit
}
```

**Computed Properties (NOT stored):**
- `spentAmount`: Sum of expense transactions for that category + month
- `isOverBudget`: `spentAmount > limitAmount` (can be computed in query)
- `progressPercent`: `Math.round((spentAmount / limitAmount) * 100)` (client-side only)

**Questions for Backend:**
1. Should budget rollover be automatic (cron job) or manual?
2. Should we store `limitAmount` as decimal (for cents) or integer (whole IDR only)?
3. How do we handle budget creation for months in the past (should be prevented)?

```typescript
  category: string;          // Optional: expense category (what is the goal for?)

```

**Questions for Backend:**
1. Should goal contributions be stored as separate transaction records?
2. How do we handle goal completion (mark as done vs. auto-archive)?
3. Should goals support multiple contributors (shared family goals)?

## Cross-Entity Relationships

### Workspace → Wallets
**Relationship Type:** One-to-Many
**Foreign Key:** `wallet.workspaceId → workspace.id`

### Workspace → Transactions
**Relationship Type:** One-to-Many (indirect, through wallet)
**Foreign Key:** `transaction.workspaceId → workspace.id`

### Wallet → Transactions
**Relationship Type:** One-to-Many
**Foreign Key:** `transaction.walletId → wallet.id` (for income/expense)
**Foreign Key:** `transaction.fromWalletId → wallet.id` (for transfer_debit)
**Foreign Key:** `transaction.toWalletId → wallet.id` (for transfer_credit)

### Workspace → Users
**Relationship Type:** Many-to-Many
**Foreign Key:** `workspace_member.workspaceId → workspace.id`
**Foreign Key:** `workspace_member.userId → user.id` (from Better Auth)

### Budget → Workspace
**Relationship Type:** Many-to-One
**Foreign Key:** `budget.workspaceId → workspace.id`

### Goal → Workspace
**Relationship Type:** Many-to-One
**Foreign Key:** `goal.workspaceId → workspace.id`

## Schema Design Decisions Required

### 1. Table Naming Convention
**Proposal:** All tables use the `dompetin_` prefix as configured in `drizzle.config.ts`

| Table Name | Drizzle Schema Name | Rationale |
|------------|-------------------|----------|
| `workspace` | `dompetin_workspace` | Workspace entity |
| `wallet` | `dompetin_wallet` | Wallet entity |
| `transaction` | `dompetin_transaction` | Transaction entity |
| `category` | `dompetin_category` | Category entity |
| `budget` | `dompetin_budget` | Budget entity |
| `goal` | `dompetin_goal` | Goal entity |
| `workspace_member` | `dompetin_workspace_member` | Workspace member junction |

### 2. ID Type Strategy
**Proposal:** Use UUIDs (string) for all primary keys, not integers

**Rationale:**
- More secure (harder to guess IDs)
- Better for distributed systems
- Aligns with Better Auth's session management
- Drizzle `text("uuid")` type is efficient

### 3. Computed/Balanced Fields
**Proposal:** For wallet balances, do NOT store `balance` as a column. Compute on the fly from the transaction ledger.

**Rationale:**
- Prevents data inconsistency (balance could diverge from transaction sum)
- Aligns with "ledger integrity" business requirement
- Single source of truth for financial data

**Implementation Options:**
1. **Cached computation:** Store computed balance and run a scheduled job to recalculate
2. **Real-time computation:** Calculate on every query from `SUM(transaction.amount)`
3. **Hybrid:** Store base balance + last transaction ID, compute delta

**Question for Backend:** Which approach do you prefer? Performance (cached) vs. Accuracy (real-time)?

### 4. Timestamp Handling
**Proposal:** Use PostgreSQL `TIMESTAMPTZ` timezone-aware columns for `createdAt` and `updatedAt`

**Rationale:**
- Indonesia timezone (WIB) handling is critical for a financial app
- Day boundaries should be consistent for budget rollover (midnight WIB)

2. **Transaction Atomicity:**

3. **Performance:**

   - Should we use database indexes for common queries (wallet list, transaction list by workspace)?
